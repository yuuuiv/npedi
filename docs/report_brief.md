## 1. 如何证明增量更新和历史回填可以回溯

“可回溯”不是把当前表再导出一次，而是保留了**从请求到事实、再到模型结果**的时间链。
这条链有三段，前两段已经建成并有数据，第三段只建了机制。

### 1.1 Bronze：请求和原始响应可追踪 ✅

每次采集写入四张表：

- `crawl_run`：任务、模式、起止时间、请求数、行数、错误、最终状态。
- `crawl_checkpoint`：任务分区、下一页、接口观测总量、最后成功时间。
- `raw_api_response`：请求指纹、业务分区、页码、响应码、payload hash、原始 JSON、抓取时间。
- `ingest_error`：错误阶段、请求参数、问题行原文（当前 850 条）。

因此可以回答：哪个任务在什么时候请求了哪个分区、当时到第几页、接口原样返回了什么、
以及这次结果后来是否被重抓或报错。

`raw_api_response` 以「请求指纹 + 页码 + payload hash」做唯一约束，
同一页重复抓取不会产生无法区分的重复原始响应。

### 1.2 Silver：当前投影与事实版本分开保存 ✅

事实表存便于分析的规范化结果，同时保留 `raw_json`、`record_hash`、业务键和入库时间。
会变化的事实**同时**追加写入 `fact_record_version`（`fact_table`、`business_key_hash`、
`observed_at`、`event_time`、`record_hash`、`normalized_json`、`raw_json`）。

同一业务键再次出现时先比 hash：内容不变则跳过，内容变化才留新版本。
**所以增量更新不会把历史状态静默覆盖掉** —— 这是“可回溯”的核心论据。

实测版本链覆盖：

| fact_table | 版本行数 | 相异业务键 | 差额 |
|---|---:|---:|---:|
| `fact_container_event` | 27,953,087 | 27,817,052 | 136,035 |
| `fact_container_vgm` | 7,650,074 | 7,602,019 | 48,055 |
| `fact_cargo_release` | 108,422 | 108,422 | 0 |
| `fact_transshipment` | 57 | 57 | 0 |

⚠️ **不要把「版本数 > 键数」当作捕获到业务变更的证据。** 实测这个差额几乎全部是
同一轮采集内的写入伪影，不是跨轮次的真实变更：

| fact_table | 多版本键 | 跨度 < 1 秒 | 1 秒–1 小时 | > 1 小时 |
|---|---:|---:|---:|---:|
| `fact_container_vgm` | 42,649 | **42,643（100.0%）** | 6 | **0** |
| `fact_container_event` | 129,329 | 128,297（99.2%） | 287 | 745 |

**根因是业务键定义漏了区分字段，不是去重逻辑有 bug。**
`timeseries.py` 的守卫只与**当前投影**比 hash：

```python
old = SELECT record_hash FROM <fact_table> WHERE business_key_hash=?
if old and old[0] == row.get(hash_field):
    return False, False          # 相同则跳过，不写版本
```

VGM 业务键是 `(箱号, 船码, 航次, operatetime, senderCode)`，**不含 `portreceiverdate`**。
接口对同一箱返回多条码头接收回执（实测同一箱有 19:37、19:38、19:39 三条），
三条塌缩成同一个键后，每写一条就把投影翻转一次，下一条相对新投影又「变了」，
于是在 **0.28 秒内**产生 19 个版本，`record_hash` 在三个值之间来回振荡：

```
TCLU6475742 / UN9595515 / 059E   （2026-08-09T06:49:37.761 → 06:49:38.045）
  v1  terminal_received_time 19:37:00   hash d08c66b504c9
  v2  terminal_received_time 19:38:00   hash a5a2d89033ad
  v3  terminal_received_time 19:39:00   hash 6b990e7e9316
  v4  terminal_received_time 19:38:00   hash a5a2d89033ad   ← 回到 v2 的内容
  ...  如此往复直到 v19，vgm_weight_kg 全程未变（14167.5）
```

`fact_container_event` 中跨度 > 1 小时的 745 个键，抽样展开后 **11 个版本的
`record_hash` 完全相同**，字段零变更 —— 同样不是业务变更。

**报告中可以站得住的表述：**

- ✅ 「事实版本表已建成并持续写入，增量更新不会原地覆盖，历史版本可按 `observed_at` 取回」
- ✅ 「同一业务键的多版本已在库中，可现场展开逐字段 diff」
- ❌ 不要说「捕获到了 4.8 万次业务变更」—— 实测跨轮次真实变更为 **0（VGM）**
- 📌 若被追问：主动说明这是**业务键粒度问题，已定位、可修**（VGM 键补入
  `portreceiverdate`，或改为对同键多行做确定性排序后取一行），比被对方指出来好

### 1.3 `as-of`：按观测时间重建当时能看到的数据 ✅（Silver 层已验证）

`backtest.py` 的 `fact_rows_as_of()` 对每个业务键取 `observed_at <= 截止时间`
范围内的最新一版，而不是直接读今天的当前表。`aggregate.py`、`curves.py`、`cluster.py`
都接受 `as_of`，结果写入独立的 `*_asof` 表，模型版本带 `@as_of=...` 后缀，不覆盖当前结果。

### 1.4 CODECO 历史回填的回溯依据 ✅

CODECO 是另一条独立事件流：

- `gate_history_candidate`：由计划事实发现的候选船×航次，含 ETA 范围、来源行数、探测状态、尝试次数。
- `gate_history_candidate_month`：记录候选在**哪些月份**真有计划证据，
  避免仅凭 `first_eta/last_eta` 把中间月份误判为存在。
- `gate_history_rejected_pair`：明确不安全的业务键（占位船码、含空白/非 ASCII 航次），
  保留原因但**不向远端发送** —— 3,555 条。这不只是省请求：
  服务端若忽略非法过滤条件，返回行会被错误归属到占位船码上。
- `gate_voyages`：每个航次分方向记录 `GATE_IN`/`GATE_OUT` 完成时间与总量，可按航次×方向断点续跑。
- `gate_events`：以接口报文 `id` 为主键的 append-only 事件流，保存 `raw_json`、`run_id`、`fetched_at`。

**`empty` 与 `complete` 都是终态但含义不同**：`empty` 表示在精确的船×航次×方向查询下
接口返回 0 行（是关于世界的事实），`complete` 表示完整页链路已入库。
报告里不要把 `empty` 说成“失败”——17.7 万个 `empty` 是采集结论，不是采集故障。

### 1.4.1 异常报文单独存库，不污染物理船数据 ✅

接口里混着虚拟船和运营聚合桶（中转、空返、堆场倒箱、吊机检修等）。这些不是真实
航次，但报文量极大——实测 `UN7654321`（中转梅山）单个航次返回 **1,633,402** 行。
若并入 `gate_events`，任何按航次或按船的统计都会被它压垮。

处理办法是双库隔离，`gate_anomaly_sidecar.py`：

- 主库 `gate_history_rejected_pair` 记下精确的 `(vesselcode, voyage)` 和判定原因，
  正常读取路径排除它们；共 3,555 条（占位船码 3,016、运营聚合桶 352、非法航次 181）。
- 报文本体存进独立的 `gate_anomaly_sidecar.sqlite`，保留原始 JSON 和分页 checkpoint。
- **响应身份绝不从查询条件回填**：响应里没有船码就保持 `NULL`，
  避免服务端忽略过滤条件时把无关行贴上占位船码。
- 判定按精确的船×航次对生效，不会因为一个船码可疑就全局封杀——同一个船码可能在
  别的时期属于真实航次。

当前侧车已全部跑完：候选 358、job complete 716 / error 0、页 18,226、
行 1,753,609、库 3.5 GiB。

这一条在报告里值得主动讲：它说明数据清洗不是"把脏数据删了"，而是**保留证据并标注原因**，
任何时候都能追溯为什么某个航次没进主数据集。

### 1.5 覆盖度边界（必须主动说明）

可回溯 ≠ 全港历史完整：

- `vesselList` 是目录快照，不等于全历史航次目录。
- 目录外候选靠计划事实发现并逐个点查，当前仍有 85,498 个待探测。
- **2020–2021 的低值是没采到，不是业务量低。** 2022 及以后完成度 99.9%，
  2021 只有 52.2%，2020 为 0。在这两年补齐前，**跨年份曲线不能解释为吞吐量趋势**，
  这是目前最容易被误读的一张图。
- `containerType`、箱重、港口、时间字段存在缺失与上游异常，聚类前必须带完整度和质量标记。

这也是 Dashboard 同时展示「数据值」和「数据覆盖/质量」、而不是只画一条漂亮趋势线的原因。

## 3. 衍生数据链路与聚类现状

```text
原始响应 / 事件流
        ↓
Bronze：运行、响应、checkpoint、schema
        ↓
Silver：规范化事实、维表、事实版本
        ↓
Gold：日/周聚合、CODECO 日聚合
        ↓
曲线：mart_curve_series
        ↓
特征：feature_series_window
        ↓
聚类、变点、异常、趋势快照
```

前四层已跑通。**从曲线往后目前不可用**，原因如下，报告中建议作为「下一步」而非「成果」呈现。

### 3.1 聚类当前是退化的 ⚠️

实测两次 `cluster_run`：

| 项 | 实测值 | 问题 |
|---|---|---|
| `sample_count` | 18 | 实体是「码头:方向」，只有 18 个 |
| `cluster_count` | 9 | 恰为 `n//2`，是代码默认公式而非数据决定 |
| `silhouette_score` | **0.0** | 簇间**完全没有分离** |
| `window_start` | **2001-06-18** | 早于任何真实数据 |

18 个实体中 **12 个的 `mean` 和 `trend_slope` 全为 0**。

### 3.2 根因：曲线被零值填充稀释

| 指标 | 周点数 | 零值占比 |
|---|---:|---:|
| `cargo_release_piece_count` | 22,971 | **100%** |
| `transshipment` | 22,971 | **99.99%** |
| `transshipment_container_count` | 22,971 | **99.99%** |
| `cargo_release` | 22,971 | 96% |
| `released_bill_count` | 22,971 | 95% |
| `vgm` | 22,971 | 69% |
| `arrival_delay` | 13,485 | 0.7% |
| `pressure_index` | 22,971 | 2% |

关键事实：`agg_flow_weekly` 的周桶跨度是 **1999-12-27 → 2027-01-11（1,395 周）**，
而 VGM 真实非零信号只在 **2018-10-15 → 2026-08-10**。
**约 71% 的周桶落在真实数据范围之外，全是零填充。**
特征向量被这些零主导，18 个实体因此彼此看起来完全一样 —— 这就是 silhouette = 0.0 的直接原因。

### 3.3 让聚类可用的四步（建议列为下一步）

1. **裁剪窗口**：`build_feature_windows` 只取真实数据范围（VGM 从 2018-10 起），
   剔除 1999–2018 与 2026-08 之后的空桶。
2. **剔除死指标**：`cargo_release_piece_count`（100% 零）、`transshipment` 系列
   （57 行事实，99.99% 零）不应进入特征向量。
3. **提高实体基数**：当前只有 18 个「码头:方向」。CODECO 已有 9,296 万事件、
   217,098 个航次，可改为按「船公司」或「航线」建实体，样本量能上两个数量级。
4. **k 不要用 `n//2`**：改为按 silhouette 扫描 k，或直接用 HDBSCAN（代码已支持）。

另外 `gate_*` 周曲线只有 470 个点，与 9,626 万条 CODECO 事件严重不匹配 ——
**大回填之后 `agg_gate_daily` 从未重建**（仍是 2,744 行，只覆盖 2021-04-16 ~ 2026-07-30）。
9,626 万条事件对应 2,744 行日聚合，这条曲线现在是失真的，
演示 CODECO 曲线前必须先跑 `rebuild_meaningful_dashboard.ps1`。

## 5. Dashboard

```powershell
.\run_report_dashboard.ps1     # 只读报告视图，端口 8080
.\run_dashboard.ps1            # 运维视图，端口 8081
```

`report_dashboard.py` 以 `mode=ro` + `PRAGMA query_only=ON` 连接，
**不会向 `npedi.sqlite` 写入任何内容**，可以放心在报告现场操作。
监听 `0.0.0.0`，同局域网内可用 `http://<本机IP>:8080` 访问。

五个页签：总览（CODECO 候选状态 + 分层数据量）、回溯证据（采集任务 + as-of 命令）、
衍生曲线（Gold 曲线 + 表预览 + CSV 导出）、聚类特征（运行历史 + 特征投影散点）、字段字典。

⚠️ 两个 `.ps1` 必须保持 **纯 ASCII**。Windows PowerShell 5.1 按 GBK 解码无 BOM 的 .ps1，
中文和 emoji 会被拆成非法字节导致 `ParserError`。

## 6. 报告建议展示顺序

1. 采集规模与证据链（§0 表 + §1.1/1.2）—— 最扎实，先立信。
2. CODECO 回填进度（§2）—— 报完成度（82.0%、分年份），**不要报完成日期**，
   理由见 §2.1。被问到什么时候完成，就答"剩约 17 小时净采集量，
   受服务端会话寿命限制，需分多天"。
3. 异常报文的处理方式（§1.4.1）—— 保留证据 + 标注原因，不是删脏数据，
   这一条通常比覆盖度数字更能说明工程质量。
4. 可回溯能力演示（§1.3）—— 讲机制，并主动说明 2026-08-04 下界。
5. 覆盖度边界（§1.5）—— 主动暴露局限，比被问出来好。重点是 2020–2021 未补齐，
   跨年曲线不可用。
6. 衍生与聚类作为**下一步计划**（§3）—— 给出根因和四步方案，
   不要展示 silhouette=0.0 的结果，也不要展示未重建的 CODECO 曲线。

演示前的必做项：若要展示任何 CODECO 曲线，**先跑一次
`rebuild_meaningful_dashboard.ps1`**（数小时），否则 9,626 万条事件只会画出
2,744 行日聚合的失真曲线。
